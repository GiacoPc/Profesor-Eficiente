# ErrorObservation — Lifecycle Contract

**Document ID:** ERROR-OBSERVATION-LIFECYCLE
**Version:** 0.1-draft
**Status:** PROPOSED / REQUIRES APPROVAL
**Branch:** `architecture/pad-clm-fdm-ape-v1.0`
**Scope:** Canonical lifecycle and authority boundary for learner `ErrorObservation`.

## 0. Purpose

This contract resolves P1 C-005 by defining `ErrorObservation` as the canonical domain record for an evidenced learner error and separating it from observations, model-generated candidates, feedback text, and derived recurrence summaries.

It does not define the final error taxonomy, severity scale, recurrence formula, persistence schema, or implementation technology.

## 1. Canonical terminology

- **Observation:** raw or directly captured learner output/data.
- **Evidence:** governed reference to an observation that is eligible for assessment.
- **Assessment:** evaluation of evidence against an explicit target/criterion, potentially probabilistic but provenance-bearing.
- **ErrorObservation:** authoritative structured record that an error condition was identified from governed evidence and accepted under the applicable validation rules.
- **ErrorObservationCandidate:** non-authoritative proposal produced by LPH/assessment capability.
- **Feedback:** learner-facing instructional response; it is not itself an error record.
- **RecurrenceSummary:** derived pedagogical summary; it is not an independent source of error truth.

## 2. Authority chain

```text
Learner output
    ↓
Observation
    ↓
Evidence
    ↓
Assessment
    ↓
ErrorObservationCandidate (optional)
    ↓
Validation / domain acceptance
    ↓
ErrorObservation (authoritative)
    ↓
CLM error/weakness state
    ↓
SDT derived error summary
    ↓
APE reinforcement decision
```

LLM/LPH output cannot bypass validation and directly create authoritative `ErrorObservation` state.

## 3. Lifecycle

The conceptual lifecycle is:

```text
OBSERVED
   ↓
EVIDENCE_LINKED
   ↓
ASSESSED
   ↓
CANDIDATE_ERROR (optional)
   ↓
ACCEPTED_ERROR
   ├──────────────→ REJECTED
   ↓
ACTIVE / TRACKED
   ↓
RESOLVED / NO_LONGER_ACTIVE
   ↓
REOPENED (only when later valid evidence supports recurrence)
```

The final persisted state vocabulary is `PENDING`; these states describe lifecycle semantics, not an implementation mandate.

## 4. Acceptance rule

An authoritative `ErrorObservation` requires:

1. stable `error_id`;
2. source `evidence_id`;
3. affected competency when determinable;
4. error category from the governed taxonomy when determinable;
5. observed form/reference;
6. target/reference when applicable;
7. assessment/provenance status;
8. explicit uncertainty when the classification is not certain;
9. acceptance under the applicable domain/evidence rules.

If evidence is insufficient or classification remains uncertain, the system must preserve that condition rather than fabricate an accepted error.

## 5. Candidate versus authoritative record

A probabilistic component may emit:

```yaml
error_observation_candidate:
  source_evidence_id: <evidence-id>
  competency_id: <id-or-null>
  category: <candidate>
  observed_form: <reference>
  target_form: <reference-or-null>
  uncertainty: <explicit>
```

This candidate is disposable and non-authoritative. Rejection, repair, or regeneration creates no historical authoritative error mutation.

Only a governed acceptance step can create/update an authoritative `ErrorObservation`.

## 6. Recurrence semantics

`recurrence_count` is not authoritative error truth.

Recurrence is a derived signal calculated from accepted error observations using a later approved policy that may consider exposure opportunities, evidence quality, temporal spacing, competency context, explicit practice opportunities, and assessment uncertainty.

Therefore:

```text
ErrorObservation history
        ↓
Approved recurrence policy
        ↓
RecurrenceSummary
        ↓
CLM / SDT
        ↓
APE
```

No numeric recurrence threshold is defined here.

## 7. Correction/feedback boundary

Feedback may be generated by LLM/LPH, but feedback does not create or erase error history.

```text
ErrorObservation
      ↓
APE pedagogical consequence
      ↓
LPH bounded task
      ↓
LLM candidate feedback
      ↓
validation
      ↓
learner delivery
```

A learner-facing correction must never be treated as proof that the underlying error was correctly classified.

## 8. Resolution and reopening

An error becomes `RESOLVED / NO_LONGER_ACTIVE` only through a governed state derivation based on later evidence and approved policy.

Historical `ErrorObservation` records remain immutable. Later evidence can establish that an error is no longer active or that a related error recurred; it does not rewrite the historical observation.

## 9. Relationship to CLM / SDT / APE

- **CLM** owns learning-state semantics for error/weakness interpretation.
- **FDM** owns the authoritative `ErrorObservation` entity, events, invariants and mutation boundary.
- **SDT** stores references/derived summaries, never replaces the error history.
- **APE** uses error/weakness state to select pedagogical action.
- **PAD** defines the pedagogical correction/reinforcement consequence.
- **LPH** may classify candidate errors and structure linguistic evidence, but cannot authorize the authoritative mutation.

## 10. Required events

The conceptual domain events are:

- `ErrorObservationCandidateProduced` — non-authoritative;
- `ErrorObserved` — authoritative accepted error record;
- `ErrorObservationStatusChanged` — governed derived status change;
- `ErrorObservationReopened` — later evidence reactivates a previously resolved pattern.

Exact event schema/versioning remains `PENDING`.

## 11. Invariants

**EO-I01 — Evidence linkage:** every authoritative error observation references source evidence.

**EO-I02 — No direct LLM mutation:** an LLM cannot create authoritative error state directly.

**EO-I03 — Candidate isolation:** candidates may be rejected without mutating historical error state.

**EO-I04 — Uncertainty preservation:** uncertain classification cannot silently become accepted error.

**EO-I05 — Historical integrity:** accepted historical observations are immutable.

**EO-I06 — Recurrence derivation:** recurrence is derived from observation history under approved policy; a counter is not authoritative.

**EO-I07 — State separation:** feedback, recurrence summary and learner-state projections cannot replace the canonical error record.

**EO-I08 — Attribution:** authoritative error transitions identify the evidence, assessment/provenance and governing policy where applicable.
